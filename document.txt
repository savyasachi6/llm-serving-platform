Cost‑efficient LLM serving essentially comes down to reusing compute (KV states) and hardware efficiently through batching, caching, and lower‑precision arithmetic, layered on top of good systems design. [runpod](https://www.runpod.io/blog/llm-inference-optimization-techniques-reduce-latency-cost)

Below I unpack batching, paged attention, KV/prompt caching, then rank other major techniques with examples, implementation sketches, and caveats.

***

## Mental model: LLM inference as batched matmul

At a low level, transformer layers are largely matrix multiplications and attention operations over token embeddings; these kernels are naturally vectorized over a batch dimension, so larger batches give the GPU more work per kernel launch and better utilization. [arxiv](https://arxiv.org/html/2412.03594v1)

Autoregressive generation complicates this by making token production sequential in time, but within each step, sequences and tokens can still be processed in parallel as long as their computation graphs are compatible (same model, similar shapes), which is what batching and paged attention exploit. [rajatpandit](https://rajatpandit.com/ai-infrastructure/continuous-batching-in-vllm)

***

## Static batching: basic throughput improvement

Static batching is the simplest optimization: group multiple prompts into one call, feed them through the model as a single batch, and return one result per input.  

For self‑hosted models, the pattern looks roughly like this:

```python
from vllm import LLM, SamplingParams  # self-hosted, GPU server
# Model is loaded once; all requests share the weights.
llm = LLM("meta-llama/Llama-3.1-8B-Instruct")

sampling_params = SamplingParams(
    max_tokens=64,
    temperature=0.7,
)

prompts = [
    "Summarize the following article ...",
    "Translate this paragraph to Spanish ...",
    "Explain this Python error message ..."
]

outputs = llm.generate(prompts, sampling_params)

for prompt, out in zip(prompts, outputs):
    print("PROMPT:", prompt)
    print("RESPONSE:", out.outputs[0].text)
```

Here the attention and MLP matmuls operate over a batch of three sequences instead of one, amortizing kernel launch and memory access overhead over more work. [jarvislabs](https://jarvislabs.ai/blog/scaling-llm-inference-dp-pp-tp)

Static batching works well when requests are homogeneous in length and latency tolerance, but it can be inefficient when short queries are stuck waiting for long ones, which motivates continuous batching.

***

## Continuous batching and parallel agents

Modern serving engines such as vLLM use continuous batching: they maintain a dynamic batch of in‑flight requests and update that batch every token generation step, immediately swapping in new requests as old ones finish. [gmicloud](https://www.gmicloud.ai/en/blog/kv-cache-management-pagedattention)

In an agentic system, you can treat each agent request as an element of a global queue; the engine continuously pulls pending agent calls into the active batch, maximizing GPU throughput while keeping per‑agent latency acceptable.

A typical architecture:

- Multiple agents (or microservices) push LLM tasks into a shared queue (e.g., Redis, Kafka).
- A dedicated “inference worker” process consumes tasks, submits them to a vLLM server, and returns responses asynchronously.
- vLLM itself implements continuous batching and paged attention; you only need to keep the queue full.

A minimal pseudo‑implementation sketch (Python, async agents):

```python
# agent_service.py
import asyncio
import uuid
from aiohttp import ClientSession

INFERENCE_URL = "http://llm-host/generate"

async def call_llm(prompt: str, metadata: dict) -> str:
    request_id = str(uuid.uuid4())
    async with ClientSession() as session:
        async with session.post(INFERENCE_URL, json={
            "id": request_id,
            "prompt": prompt,
            "metadata": metadata,
        }) as resp:
            data = await resp.json()
            return data["completion"]

async def agent_loop(agent_state):
    while True:
        prompt = build_prompt(agent_state)
        completion = await call_llm(prompt, {"agent": agent_state.name})
        agent_state = update_state(agent_state, completion)
```

On the serving side, vLLM (or TensorRT‑LLM, SGLang, etc.) maintains the KV cache and batch; your agents simply issue parallel HTTP requests, and the engine’s scheduler merges them into an efficient continuous batch. [runpod](https://www.runpod.io/blog/llm-inference-optimization-techniques-reduce-latency-cost)

Continuous batching is particularly valuable for agent swarms and multi‑tenant APIs, where there is a high volume of small, overlapping requests.

***

## Paged attention and KV‑cache memory management

### What KV cache does

During prefill (processing the input prompt), the model computes key and value tensors for each token and stores them in a KV cache; subsequent decoding steps reuse these tensors instead of recomputing attention over the entire prefix at every token. [arxiv](https://arxiv.org/pdf/2309.06180.pdf)

This reuse is what makes long‑context generation tractable: the cost per new token scales mainly with the new attention against the fixed prefix plus any new tokens, not with the full sequence length.

### Traditional KV cache problems

Naïve KV cache allocation reserves a large contiguous buffer per sequence, sized for its maximum allowed length; with variable‑length prompts and outputs, this leads to severe fragmentation and wasted GPU memory, particularly when many short sequences share the same upper bound. [developers.redhat](https://developers.redhat.com/articles/2025/07/24/how-pagedattention-resolves-memory-waste-llm-systems)

Moreover, shards of KV cache can easily become stranded: when some sequences finish early, their allocated memory may not be reused efficiently if the engine insists on contiguous blocks.

### Paged attention: “virtual memory” for KV states

Paged attention, introduced by vLLM, treats KV cache as paged virtual memory:

- Split each sequence’s KV cache into fixed‑size blocks (pages), e.g., 128–256 tokens per block. [arxiv](https://arxiv.org/pdf/2309.06180.pdf)
- Allocate pages on demand as sequences grow, rather than preallocating the full maximum. [gmicloud](https://www.gmicloud.ai/en/blog/kv-cache-management-pagedattention)
- Use an indirection (page table) to map logical token positions to physical blocks, so blocks can be non‑contiguous.
- Deallocate and recycle pages as soon as a sequence finishes or is truncated. [gmicloud](https://www.gmicloud.ai/en/blog/kv-cache-management-pagedattention)

Because blocks are uniform, the allocator can pack KV pages tightly and reuse them across requests, substantially increasing effective GPU capacity (often 2–4× more concurrent tokens). [developers.redhat](https://developers.redhat.com/articles/2025/07/24/how-pagedattention-resolves-memory-waste-llm-systems)

Crucially, paged attention also enables sharing KV blocks between batched requests that share identical prefixes, which synergizes with prompt caching and common system prompts. [gmicloud](https://www.gmicloud.ai/en/blog/kv-cache-management-pagedattention)

### Where KV cache lives and how long it persists

In self‑hosted engines like vLLM and TensorRT‑LLM, KV cache typically lives entirely in GPU memory and exists only for the lifetime of in‑flight sequences; once a request completes and its pages are freed, those KV states are gone unless you explicitly implement a higher‑level prompt cache. [arxiv](https://arxiv.org/pdf/2309.06180.pdf)

Managed APIs (OpenAI, Anthropic, Vertex AI, Azure) formalize KV reuse as “prompt caching” and expose TTL policies, where KV tensors may be retained in GPU memory or GPU‑local storage for minutes to hours and reused across requests that share a prefix. [arxiv](https://arxiv.org/html/2601.06007v2)

***

## Prompt caching: compute reuse across requests

### Conceptual distinction: KV caching vs prompt caching

It is helpful to distinguish:

- KV caching: intra‑request reuse during autoregressive decoding; every modern transformer implementation does this. [arxiv](https://arxiv.org/html/2601.06007v2)
- Prompt caching: inter‑request reuse of KV tensors when different API calls share an identical prefix; this is a product feature that piggybacks on KV caching but operates at the serving layer. [ibm](https://www.ibm.com/think/topics/prompt-caching)

Prompt caching stores the KV tensors for a stable prefix (system prompt, tool definitions, long static context) and reuses them for future requests that start with the same token sequence, avoiding recomputation of that prefix and lowering both latency and input‑token cost. [ibm](https://www.ibm.com/think/topics/prompt-caching)

### Mechanics: exact prefix matching and breakpoints

Most providers expose prompt caching as a prefix‑match mechanism:

- When a request is processed, the service tokenizes the prompt and identifies cacheable segments (often at fixed boundaries of 128–256 tokens). [developers.openai](https://developers.openai.com/api/docs/guides/prompt-caching)
- The KV tensors for those segments are stored under a cache key (automatic hashing or a user‑supplied key).
- On subsequent calls, if the first N tokens of the prompt are exactly identical to a cached prefix and the model and decoding parameters match, the service reuses the cached KV tensors and continues from where the prompts diverge. [learn.microsoft](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/prompt-caching)

Even a single token change in the cached prefix invalidates reuse beyond that token; this is why providers emphasize strictly stable system prompts and tool descriptions for effective caching. [mager](https://mager.co/blog/2026-04-29-claude-prompt-caching/)

### Provider policies and TTL (how long KV cache is kept)

Policies differ slightly, but the broad picture is:

- OpenAI / Azure OpenAI: automatic caching for prefixes ≥1024 tokens; cache hits at 128‑token increments; TTL parameter (`prompt_cache_options.ttl`) sets a minimum retention of about 30 minutes for GPT‑5.6+ families, with practical eviction often after 5–10 minutes of inactivity for in‑memory caches and up to 24 hours for extended retention that offloads KV tensors to GPU‑local storage. [youtube](https://www.youtube.com/watch?v=tECAkJAI_Vk)
- Anthropic (Claude): implicit prompt caching with a default 5‑minute TTL, refresh on each use; optional 1‑hour TTL at higher write cost (`cache_control: { type: "ephemeral", ttl: "1h" }`); minimum cacheable lengths vary by model (often 512–4096 tokens), and cache entries are deleted promptly after TTL expiration. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Vertex AI (Gemini): implicit and explicit “context caching,” with minimum cacheable size around 2048 tokens and retention up to 24 hours, subject to load; caches are always cleared within a day. [cloud.google](https://cloud.google.com/blog/products/ai-machine-learning/vertex-ai-context-caching)

In all cases, KV cache for prompt caching is ephemeral and isolated per tenant; it is not persisted at rest as raw text, but as hashed or compressed KV tensors and metadata. [prompthub](https://www.prompthub.us/blog/prompt-caching-with-openai-anthropic-and-google-models)

So, in practice:

- If you are using a managed API, KV cache for prompt caching lives for a few minutes by default, with optional extension to an hour or a day depending on provider and plan. [hidekazu-konishi](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html)
- If you self‑host with vLLM/TensorRT, KV cache for ordinary decoding exists only while the request is active; for cross‑request reuse you must implement your own prompt‑module cache (e.g., Prompt Cache, vLLM plugins). [proceedings.mlsys](https://proceedings.mlsys.org/paper_files/paper/2024/file/a66caa1703fe34705a4368c3014c1966-Paper-Conference.pdf)

### Implementation example: OpenAI‑style prompt caching

A simplified pattern, using an API that exposes `prompt_cache_options` and a cache key:

```python
from openai import OpenAI
client = OpenAI()

SYSTEM_PROMPT = """
You are a precise software engineering assistant.
Follow the given function signatures and do not change them.
...
"""

# First call: write cache
resp1 = client.responses.create(
    model="gpt-5.6-mini",
    input=[
        {
            "role": "system",
            "content": SYSTEM_PROMPT,
            "cache_control": {
                "type": "ephemeral",  # in-memory or extended, depending on provider
                "ttl": "30m",         # minimum lifetime, actual may be longer
            },
        },
        {
            "role": "user",
            "content": "Explain this Python stack trace:\n" + error_text,
        },
    ],
    metadata={"cache_key": "se-assistant-v1"},
)

# Subsequent call, within TTL, identical system prompt:
resp2 = client.responses.create(
    model="gpt-5.6-mini",
    input=[
        {
            "role": "system",
            "content": SYSTEM_PROMPT,
            "cache_control": {
                "type": "ephemeral",
                "ttl": "30m",
            },
        },
        {
            "role": "user",
            "content": "Now help me refactor this code:\n" + code_snippet,
        },
    ],
    metadata={"cache_key": "se-assistant-v1"},
)
```

The first request pays a higher price to write the cached KV tensors; subsequent requests pay a small “cache read” price and avoid recomputing the system prompt, reducing effective input cost and time‑to‑first‑token, especially when the prefix is long. [developers.openai](https://developers.openai.com/api/docs/guides/prompt-caching)

### When prompt caching helps most

Prompt caching is most beneficial when:

- You have long, stable prefixes (system messages, tool schemas, policy documents, reference corpora) reused across many calls. [hidekazu-konishi](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html)
- Agents or workflows fork multiple branches from a common base prompt (e.g., many tools invoked off the same context), so many requests share the first 1024–2048 tokens. [community.openai](https://community.openai.com/t/using-same-prompt-cache-key-in-multiple-parallel-conversations/1371443)
- You run agentic workloads with bursts: extended TTL (1h–24h) can maintain hot caches across a batch, even when individual requests are separated by minutes. [aws.amazon](https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-bedrock-one-hour-duration-prompt-caching/)

It is less effective for very short prompts, highly dynamic prefixes, or heterogeneous models/parameters.

## Ranking other major cost‑efficiency techniques

Beyond batching, paged attention, and prompt caching, several other techniques routinely deliver substantial cost reductions. A reasonable ROI ordering (assuming you already have basic batching) might be:

1. Quantization (VRAM and hardware class).
2. Model choice, distillation, and pruning.
3. Speculative decoding.
4. Parallelism strategies (tensor/pipeline/data parallel).
5. Prompt and context design (shorter inputs, RAG).
6. Engine selection and deployment mode (vLLM vs TensorRT‑LLM vs SGLang).
7. Sampling and stopping controls (max tokens, early stopping).

Below I unpack each, focusing on implementation details, use cases, and limitations.

***

## Quantization: fewer bits per weight

Quantization reduces weights from full precision (e.g., FP16/BF16) to FP8 or INT4/INT8, shrinking the model and KV cache, and enabling cheaper GPUs or larger batch sizes without changing the architecture. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)

Techniques such as AWQ (Activation‑aware Weight Quantization) or GPTQ aim to preserve quality by allocating more precision to more sensitive weights, and modern FP8 quantization on H100‑class hardware often achieves near‑parity quality with substantial VRAM savings. [linkedin](https://www.linkedin.com/posts/pallavi-shekhar_5-llm-optimization-techniques-lets-understand-activity-7442067281532325888-4aOS)

Implementation sketch (offline, via AutoAWQ):

```python
from autoawq import AutoAWQForCausalLM
from transformers import AutoTokenizer

model_name = "meta-llama/Llama-3.1-8B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(model_name, use_fast=True)
model = AutoAWQForCausalLM.from_pretrained(
    model_name,
    quantize="w4a16",  # 4-bit weights, 16-bit activations
)

model.save_quantized("llama-3.1-8b-awq")
```

You then serve the quantized checkpoint with vLLM or TensorRT‑LLM; the smaller footprint often lets you move from expensive A100s to cheaper L4s or run more replicas per GPU. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)

Limitations and misuses:

- Aggressive quantization (4‑bit everything) can harm alignment and factuality, especially for small models or niche tasks; test on your workloads and consider mixed precision (e.g., keep embeddings and output heads higher‑precision). [linkedin](https://www.linkedin.com/posts/pallavi-shekhar_5-llm-optimization-techniques-lets-understand-activity-7442067281532325888-4aOS)
- Quantization does not fix slow kernels or poor batching; it reduces static cost but must be combined with serving‑side optimizations to see full benefits. [runpod](https://www.runpod.io/blog/llm-inference-optimization-techniques-reduce-latency-cost)

***

## Distillation and pruning: right‑sizing capability

Knowledge distillation trains a smaller “student” model to emulate a larger “teacher,” preserving behaviour on target tasks while cutting parameter count and inference cost. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)

Pruning removes redundant weights or entire heads/neurons based on salience criteria, further tightening the model, often with fine‑tuning to recover performance. [linkedin](https://www.linkedin.com/posts/pallavi-shekhar_5-llm-optimization-techniques-lets-understand-activity-7442067281532325888-4aOS)

In practice:

- Identify what you actually need (e.g., code completion vs general reasoning).
- Fine‑tune or distill a mid‑size model (e.g., 7–8B) on your domain instead of relying on a huge general‑purpose model.
- Combine with quantization to push cost down further.

Distillation/pruning trade accuracy for efficiency, and are best justified when you can monitor task‑level metrics and accept some degradation in exchange for predictable cost savings. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)

***

## Speculative decoding: parallelizing verification

Speculative decoding uses a small, fast “draft” model to propose several candidate tokens; the large target model then verifies these candidates in a single forward pass, accepting as many as are consistent with its distribution. [linkedin](https://www.linkedin.com/posts/pallavi-shekhar_5-llm-optimization-techniques-lets-understand-activity-7442067281532325888-4aOS)

The key observation is that verifying \(K\) tokens in parallel costs roughly the same as verifying one token, because the transformer’s forward pass over a sequence of length \(K\) can be vectorized over that batch of tokens. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)

Implementation pattern:

- Run a lightweight model to generate a short continuation (e.g., 4–8 tokens).
- Feed those candidate tokens to the large model in one call and compare probabilities.
- Accept the longest prefix of candidates that the large model deems plausible.
- If none match, fall back to the large model’s own generation.

Some serving frameworks now expose speculative decoding as a configuration option; others require custom integration.  

Limitations and when not to use:

- It increases architectural complexity and introduces two models; if your throughput is dominated by short prompts or strict latency requirements, the coordination overhead may outweigh gains. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)
- Speculative decoding shines for long‑form generation, not for single‑token classification or short replies. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)

***

## Parallelism: tensor, pipeline, and data

Parallelism strategies split computation across multiple GPUs:

- Tensor parallelism: divide matrix multiplications within each layer across devices; all GPUs collaborate on a single request and synchronize after each layer. [jarvislabs](https://jarvislabs.ai/blog/scaling-llm-inference-dp-pp-tp)
- Pipeline parallelism: assign different layers to different GPUs; tokens flow along the pipeline.
- Data parallelism: replicate the model on multiple GPUs; each replica processes independent batches. [jarvislabs](https://jarvislabs.ai/blog/scaling-llm-inference-dp-pp-tp)

For inference:

- Tensor parallelism is useful for low‑latency serving of large models that do not fit on a single GPU, provided you have fast interconnects (NVLink, IB). [jarvislabs](https://jarvislabs.ai/blog/scaling-llm-inference-dp-pp-tp)
- Data parallelism is simpler and pairs well with vLLM’s batching; each replica runs continuous batching, and an upstream router performs load balancing. [runpod](https://www.runpod.io/blog/llm-inference-optimization-techniques-reduce-latency-cost)

Parallelism improves throughput and capacity, but increases infrastructure complexity and sensitivity to network performance; misconfigured parallelism can introduce nondeterminism or bottlenecks if communication dominates computation. [thinkingmachines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)

***

## Prompt and context design: fewer tokens, better retrieval

Reducing input length is itself a powerful cost lever: prompt caching is only one route; careful prompt engineering and RAG design can substantially cut redundant context.  

Strategies:

- Separate stable prefixes (system prompts, tool schemas) from dynamic content and make them cacheable; keep dynamic parts short and task‑specific. [arxiv](https://arxiv.org/html/2601.06007v2)
- Use retrieval‑augmented generation with focused chunks instead of dumping entire documents; tune chunk size and number‑of‑chunks per query.
- Avoid verbose conversational history when it is not needed; summarize prior turns and cache those summaries when they become stable.

These techniques interact favourably with prompt caching and paged attention: shorter, cleaner prompts hit caches more reliably and generate less KV state to manage per request. [cloud.google](https://cloud.google.com/blog/products/ai-machine-learning/vertex-ai-context-caching)

***

## Engine selection and deployment mode

Serving engines are not interchangeable; each is tuned for different workloads:

- vLLM: strong for general chat and long contexts, continuous batching and paged attention at scale. [docs.vllm](https://docs.vllm.ai/en/latest/design/paged_attention/)
- TensorRT‑LLM: often preferred when you need highly optimized kernels on NVIDIA hardware for specific models, sometimes with lower latency for single requests. [runpod](https://www.runpod.io/blog/llm-inference-optimization-techniques-reduce-latency-cost)
- SGLang and similar: oriented toward agentic and structured‑output workloads, emphasizing flexible routing and JSON generation. [runpod](https://www.runpod.io/blog/llm-inference-optimization-techniques-reduce-latency-cost)

Deployment choices:

- Single large GPU with high batch sizes vs multiple smaller GPUs with data parallelism.
- Autoscaling vs static capacity; pay‑as‑you‑go cloud vs reserved instances.

Misuse patterns:

- Running vLLM without enough traffic to maintain continuous batches, leading to underutilization.
- Choosing a speculative‑decoding‑optimized engine for workloads where almost all calls are single‑token classification.

Matching engine and deployment mode to workload characteristics (traffic shape, context length, latency tolerance) is a high‑ROI systems decision. [rajatpandit](https://rajatpandit.com/ai-infrastructure/continuous-batching-in-vllm)

***

## Sampling, max tokens, and stopping

Finally, simple generation parameters affect cost directly:

- `max_tokens`: hard cap on output length; liberal defaults (e.g., 1024) often waste tokens unless you explicitly need long answers.
- Stop sequences: define task‑specific stop conditions to prevent rambling completions.
- Temperature and top‑p/top‑k: while they mainly affect quality and diversity, lower variance generation can reduce retries and post‑processing.

In agent systems, tight control over output length per turn, combined with caching of stable prefixes, often yields sizeable cost savings with minimal complexity. [hidekazu-konishi](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html)

***

## Putting it together: design patterns and cautions

A pragmatic cost‑efficient design for multi‑agent LLM systems tends to layer these techniques:

- Quantize and, where possible, distill to a smaller model to fit inexpensive GPUs. [linkedin](https://www.linkedin.com/posts/pallavi-shekhar_5-llm-optimization-techniques-lets-understand-activity-7442067281532325888-4aOS)
- Serve via vLLM or a similar engine configured for continuous batching and paged attention, so parallel agents naturally produce high‑utilization batches without per‑agent coordination. [docs.vllm](https://docs.vllm.ai/en/latest/design/paged_attention/)
- Structure prompts with a long, stable system/tool prefix, cached with appropriate TTL, and a short dynamic tail; use provider‑specific prompt caching controls or implement prompt modules in self‑hosted setups. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Where long‑form generation is central, consider speculative decoding and monitor its gains; where requests are short and heterogeneous, focus instead on batching and cache hit rates. [digitalocean](https://www.digitalocean.com/community/tutorials/llm-inference-optimization-quantization-to-speculative-decoding-part-2)
- Use telemetry (Prometheus metrics, cache hit/miss logs) to avoid speculative optimizations: measure GPU cache usage, batch sizes, KV memory, and prompt cache statistics to see where bottlenecks and savings actually lie. [gmicloud](https://www.gmicloud.ai/en/blog/kv-cache-management-pagedattention)

Limitations and “how not to use” these tools generally boil down to misalignment between the technique and the workload: applying prompt caching to tiny, constantly changing prompts; over‑quantizing a model for subtle reasoning tasks without evaluation; or building elaborate parallelism on top of sparse traffic, where simpler single‑GPU setups would suffice. Careful empirical measurement and modest experimentation around your actual traffic and quality requirements are usually more valuable than chasing every new optimization in the abstract. [cloud.google](https://cloud.google.com/blog/products/ai-machine-learning/vertex-ai-context-caching)
